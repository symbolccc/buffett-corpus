# 对抗评审协议

## 循环（借鉴 mimeo 阶段化 + 本库反例交叉引用）

    判决（run-criteria.py）
      → 红队质询（adversarial_review.py 生成 MANDATORY/ADVISORY 清单）
      → 分析者逐条回答（写进 REVIEW 文件的"回答"栏）
      → 有改变才有效：至少一个 MANDATORY 回答修正了判决表述
      → 重跑引擎 → 终版结论

## 为什么必须有这一层

判据引擎是"证据组织器"：给定输入，它只会把证据组织成支持判断的形式。
确认偏误在系统层面存在，不是靠提醒能解决的——所以强制反面搜索，
并把"历史上同类信号失败过几次"（反例库）直接注入质询。

## 通过标准（三条全满足才能出最终结论）

1. 所有 MANDATORY 项有具体回答；
2. 至少一个回答实质修改了判决表述；
3. 扰动测试给出了具体翻转点数字。

## 与其他层的接口

- 反例库（criteria/counter-examples.json）：每条判据自动挂历史失败案例
- 归属层（criteria/attribution.json）：引用思想时检查发明人，防止错误包装
- 时代分期（corpus-index/eras.json）：E4 期（Abel）数据不得进入巴菲特判据解读
